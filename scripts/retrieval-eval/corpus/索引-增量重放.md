# 索引：增量重放

## 事件从哪来

资料内容每次变化都会在同一个事务里写一条 outbox 事件（`kb_outbox_events`）。写向量和写事件在同一事务，所以"内容改了但索引不知道"这件事不会发生。

## 检查点

索引记住 `last_applied_event_id`。重放时按事件 ID 升序取大于检查点的事件，逐条应用，应用成功就推进检查点。

幂等键：`document:{id}:v{version}:published`、`document:{id}:deleted`。同一条事件重放多次结果一致，所以进程中途被杀也不会把索引搞坏。

## 三种处理

- **发布**：资料版本变化 → 删旧版本切片、写新切片、算向量。
- **删除**：资料被删 → 删切片、删向量。
- **跳过**：事件属于已退役的索引（老索引不该再追新内容）。

## 什么时候需要全量重建

增量重放解决不了两件事：

1. 换了向量模型（旧向量空间作废）
2. 切片策略变了（切片 ID 全变，没法逐条对应）

这两种情况走全量重建，且重建的是**阴影索引**，不是活动的那个。

## 排查卡住

`last_applied_event_id` 长时间不动，先看是否有事件一直失败。失败事件不会被跳过，它会把检查点卡在那里——这是有意的，静默跳过一个事件等于永久缺一块内容。
