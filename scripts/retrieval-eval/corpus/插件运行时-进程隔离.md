# 插件运行时：进程隔离

## 结论先行

Windows 上插件进程跑在 **AppContainer** 里，这是内核级隔离，不是"约定不访问"。用户在不知情的情况下也不会被插件偷读文件——因为操作系统直接拒绝。

## 具体做法

1. 给每个插件建一个 AppContainer profile，名字是 `<ContainerNamePrefix>.<插件标识>`，默认前缀 `MyFirstMafAgent.Plugin`。
2. 派生出的 SID 形如 `S-1-15-2-<hash>`，它出现在 `icacls` 输出里，是确认隔离真的生效的最直接证据。
3. 目录授权走 `icacls` 等价的 ACL 写入：插件目录只授 `(OI)(CI)(RX)`，数据目录只授 `(M)`。
4. 用 `STARTUPINFOEX` + `PROC_SECURITY_CAPABILITIES` 创建进程，能力 SID 里只放用户授予的那几个。

## 一条硬规矩：绝不改祖先目录的 ACL

只对**叶子目录**追加继承式 ACE。给祖先目录（尤其是驱动器根 `C:\`）写 ACL 会触发整盘递归的继承重整，实测能把进程卡死几分钟。也不该这么做——叶子目录上的可继承 ACE 已经足够让子进程读到内容。

同理：重复启动不要每次都重写 ACL。已经有等价规则时直接跳过，否则每次启动都在改安全描述符。

## 平台边界

Linux 的 `bwrap`/`unshare`、macOS 的 `sandbox-exec` 都**没有实测过**，所以代码里如实标注为"未支持"，而不是假装隔离。在没有隔离的平台上，权限检查仍然生效，但只是宿主自己的检查。

## 一个坑

容器内跑 node 时会报 `EPERM: lstat 'C:\'`，因为 symlink 解析被容器边界挡住。解法是注入 `NODE_OPTIONS=--preserve-symlinks-main`，不是放宽权限。
