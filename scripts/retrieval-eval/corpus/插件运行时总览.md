# 插件运行时总览

## 一张图说完

```
发现 → 校验清单 → 等待授权 → 启动进程（隔离容器）
     → 协议握手 → 能力入表 → 健康检查（周期性）
     → 调用（超时可配）→ 升级/排空 → 卸载
```

## 各阶段一句话

- **发现**：扫描 `App_Data/plugins/` 下的目录，认 `manifest.json` / `plugin.json` / `skill.json`；压缩包解压后多一层时会下探。
- **校验**：清单字段归一化（别名、数组命令行、顶层 requires），认不出的权限词直接报错。
- **授权**：未授权不启动进程，界面上发起授权。
- **启动**：Windows 上在隔离容器内启动；其它平台按未支持标注。
- **握手**：确认协议版本、拉取工具列表，超时和重试策略见对应章节。
- **健康检查**：周期探活，连续失败会标记不健康。
- **调用**：走统一的能力调用通道，带副作用等级与确认要求。
- **升级**：先排空再换版本，失败回滚。
- **卸载**：停止进程、可选删除数据目录。

## 设计取舍

1. **以 MCP 为骨**：现成的 MCP server 不用改一行就能载入，`initialize` / `tools/list` / `tools/call` 全部按标准走。生态里的清单词汇做别名兼容。
2. **权限必须由用户授予**："不询问即被拒绝"比"先跑起来再说"更值得。
3. **失败要能解释**：每个失败状态都带可读原因，而不是一个通用错误码。

## 这一篇不写具体数值

超时、重试次数、保留天数都在各自章节里，因为它们是**可配置项**，集中抄一遍只会产生两份会互相矛盾的说明。
